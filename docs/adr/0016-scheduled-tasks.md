# ADR 0016 — Scheduled tasks: agents that run on a timetable

Status: accepted

## Context

Everything in the app assumed a person at the keyboard: a chat that never ends is the only way to have an agent "check this every day", and it burns context for nothing between the checks. What was wanted: *every morning look for new job offers*, *report a few stock prices at 17:00* — a prompt, a timetable, and the answer waiting in Gazeta.

## Decision

1. **A schedule is a saved prompt plus a timetable** (`schedules.ts`, tables `schedules` and `schedule_runs`, migration 2): name, prompt (≤ 8000 characters), a 5-field cron expression or `@hourly`/`@daily`/`@weekly`/`@monthly`, an IANA time zone, optionally a model and a project, and `allowPaid`. Cron is parsed by `croner`, in the schedule's own zone, so daylight-saving changes do what a person expects. At most 50 schedules, and no more often than every 15 minutes: every firing is a full agent turn. The same field also takes **one moment** (`2026-10-24T08:30`, read in the schedule's zone) for a one-time task, and a task can be **limited to N runs** (migration 3: `max_runs`, `run_count`); a used-up task stays in the list as "finished" until it is edited or deleted. Skipped slots and "Run now" do not use up a limited task's runs.
2. **Every run is an ordinary chat** titled `⏰ <name> · <time>`, created fresh with the prompt as its first message. The result is therefore inspectable and can be continued by hand; nothing about a run lives in a private format. A run's history (100 kept per schedule) links to its chat.
3. **Nobody is watching, so nothing may wait for a person unless the task says so.** A turn started by a schedule is *unattended*. Whatever is already allowed (a standing "Always" grant, `policy.json`) simply runs. What needs approval goes through **the same `WebApprovalGate` as in a chat — there is no second approval mechanism**: the request is an ordinary pending approval, and Gazeta lists every pending approval (from any chat or run) as an entry among its other items, with the very card the chat shows (`ApprovalCard`), answered through the same endpoint. What the run does meanwhile is a per-task setting (`approval_wait_min`, migration 3): **0** — the call is refused at once, the model is told why and carries on, and the request stays in Gazeta as a *late* entry (only "Always allow" and "Dismiss" mean anything for a run that is over; a request is kept for a week, at most 50); **N minutes** — the run pauses on the pending approval, and goes on without the call if nobody answers in time. A dangerous-looking call is never covered by "Always". `request_human_input` is forced non-blocking. The system prompt says all this and gives the step limit, and asks for one complete final answer, because that answer is the report. The full-screen approval modal no longer covers Gazeta: while Gazeta is open the requests are in it.
4. **The result goes to Gazeta** as a `report` from the agent `schedule` (unless the agent posted its own report). A failure — no usable model, a refused paid model, a turn that errored — also lands there as "Scheduled task failed: <name>", so a daily job never goes quiet unnoticed.
5. **The cost guard applies.** With no model chosen, a run uses the *Agents* slot; unless the task says `allowPaid`, a model that is not tagged `free` is refused with a message that names the checkbox. There is no silent fallback to another model. A run is capped at `SCHEDULE_MAX_STEPS` model steps (default 25).
6. **The scheduler is conservative** (`scheduler.ts`). It looks at the clock every 30 s. A schedule's next time is moved forward *before* its run starts, so a crash or a slow run can never fire the same slot twice. A run still going when the next slot comes is skipped, not stacked, and the history says so. If the app was down, a slot missed by up to 2 h is run once, late; older ones are skipped with a reason. At most 2 scheduled runs go at once. Runs cut off by a shutdown are marked as interrupted at the next start. "Run now" starts a run without touching the timetable.
7. **The UI** is a *Scheduled tasks* window (sidebar): list with next run, last result, run now, pause, edit, delete with confirmation, per-task history that opens the run's chat, and a form with presets, a custom cron field and a live preview of the next five times from the server's own parser. It refreshes on the `schedule:changed` event and polls while open.
8. **Ghost projects cannot have schedules**: a ghost chat is promised never to leave the machine and is created by a person present.
9. **The agent can schedule from an ordinary chat** (`schedule-tools.ts`, migration 4: `conversation_id`, `chain`), on the same engine:
   - `schedule_wakeup({ prompt, minutes | at })` — wake itself up once, *in the same chat*, up to 14 days ahead. **No approval**: it only continues what is already going on. It is a one-time schedule bound to the chat: when it fires, the prompt arrives as a new message and an unattended turn runs there (approvals wait 30 min in Gazeta, then are refused); the answer stays in the chat, and the alarm is deleted. It is the only tool a wake-up turn gets besides the usual ones, so an agent can poll ("check again in 10 minutes") but cannot create tasks from a task. Limits: 5 waiting per chat (100 overall, outside the user's 50), and a chain of 10 wake-ups without a message from the user is cut (`chain`). A wake-up overdue because the app was down still runs, late, and waits for a free slot instead of being dropped; deleting the chat cancels its wake-ups. Wake-ups appear in the Scheduled tasks window as "The assistant will continue this chat" (open chat, pause, cancel).
   - `create_scheduled_task({ name, prompt, cron | at, timezone?, max_runs? })` — a task of its own (a fresh chat each time, free models, results in Gazeta). It **goes through the approval gate** like any side effect, and shows the user the name, prompt and timetable on the card. Not offered in a ghost chat or in unattended runs.
   The model has no clock, so the system prompt carries the date and the user's time zone (`TZ`) on a line of its own (it changes once a day, so it does not spoil prompt caching), and a refused moment comes back with "now it is …".

## Consequences

- A scheduled task can do what the person already allowed in normal chats and nothing more; the first run is the moment to find out what is missing (the chat shows which call was refused), then answer "Always" to it once in a normal chat.
- Costs are bounded by the interval floor, the step limit and the free-model default, but a task that is allowed paid models and runs every 15 minutes still adds up; each run is a chat, so its usage shows up like any other chat's.
- Timetables are evaluated by the app, so nothing runs while it is down; a short outage is covered by the catch-up, a long one is reported as skipped.
- A local bridge, voice and the mobile assistant can reuse the same mechanism (a prompt run unattended with a result in Gazeta); none of them is part of this decision.
